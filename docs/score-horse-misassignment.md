# 発見: 本番 scores-cache で「馬 ↔ スコア」の対応がずれている

④のバックフィル小規模テスト中に、遡及導出したスコアを本番のライブ算出値と
突き合わせて発見した。**④とは独立の、既存の不具合。**

## 1. 症状

小規模テスト（2026-07-11/12 の 40R・507頭）で本番と比較した結果:

| レース単位 | 件数 |
|---|---|
| 完全一致（ずれ無し） | 26R |
| **値の集合は同じだが並びが違う** | **14R** |
| 集合も違う | 0R |

馬単位の一致率は 332/507 = **65.5%**。

「集合も違う」が 0R であることが決定的で、これは
**バックフィルが違う値を計算したのではなく、同じ値が別の馬に付いている**
ことを意味する。

### 実例: 2026-07-12 函館9R 北海ハンデキャップ

| 馬番 | 馬名 | 本番 form | バックフィル form |
|---|---|---|---|
| 1 | マイネルフーガ | 56 | 48 |
| 4 | ウィルサヴァイブ | 85 | 56 |
| 9 | エーデル | 81 | 23 |
| 10 | コッツォリーノ | 28 | 85 |
| 12 | フォルテフィオーレ | 65 | 81 |

本番の「馬番1=56」はバックフィルでは馬番4の値、「馬番9=81」は馬番12の値。
値そのものは両者で完全に同じ集合。単純なシフトではなく **並び替え**
（shift=±1〜3 のいずれでも一致率は上がらない）。

### どちらが正しいか

エーデル(2021105321) の cutoff 前の直近5走は
`13/13着, 5/8着, 10/13着, 9/16着, 8/13着`。
`calcFormScore` の重み(0.40/0.25/0.15/0.12/0.08)で手計算すると

```
(0×0.40 + 42.9×0.25 + 25.0×0.15 + 46.7×0.12 + 41.7×0.08) = 23.4 → 23
```

**バックフィルの 23 が正しく、本番の 81 はエーデルの成績からは出ない値。**

## 2. 原因

`scripts/fetch-races.ts:161`

```ts
horses: info.horses.map((h, i) => ({
  id: rid * 100 + i + 1,   // ← 配列インデックス由来 = 位置に依存する ID
  ...
```

馬の識別子が **出馬表の配列順** で決まっている。`netKeibaHorseId` という
安定した識別子が同じレコードの中にあるのに、そちらを使っていない。

一方 `scores-cache.json` はこの `id` をキーにスコアを保存する
(`fetch-scores.ts:143` `scores[horse.id] = {...}`)。

したがって:

1. `fetch-races` が走る → 配列順で id を採番
2. `fetch-scores` が走る → その id でスコアを保存
3. **`fetch-races` が再度走り、出馬表の並びが変わる** → 同じ id が別の馬に付く
4. スコアは 2. の対応のまま → **id 経由の join が別の馬を指す**

### 並びが変わる契機（推定）

ずれていた14Rは **すべて 2026-07-12（日曜）** で、07-11（土曜）は全レース一致だった。
枠順確定前は出馬表が馬番順に並ばないため、
**枠順確定前にスコアを算出し、確定後に fetch-races が再取得した回で並びが変わる**
のが契機と考えられる。日曜のほうが確定が遅いこととも整合する。

※ この «契機» の部分は状況証拠からの推定。
   «位置依存 ID + 再取得での並び替え» という機序自体は上記の実データで確定している。

## 3. 影響範囲

### バックテスト（②③・v2 vs v3 の A/B）

`buildRaces()` は `scoresById[h.id]` で join しているため、
**ずれたレースでは各馬に他馬の formScore/pedigreeScore が入った状態で
EV・edge を計算している。** 小規模テストの比率をそのまま当てると、
v2 データの約1/3の馬が影響を受けている可能性がある。

`docs/backfill-leak-ab-v2-v3.md` の結論（AUC・ROI）は、この汚染を含んだ数字。
ただし v2 と v3 は **同じ join を通っているので A/B の比較自体は同条件**であり、
「リーク除去で結論が壊れない」という手順3のゲート判定は維持される。
壊れるのは «絶対値としてのモデル性能» のほう。

### 本番のライブ表示

同じ join を UI も通るため、**枠順確定後に fetch-races が再取得した週は、
画面上のスコアも別の馬のものを表示している可能性がある。**
これはバックテストだけの問題ではない。

### バックフィル（④）

**影響しない。** `backfill-derive.ts` は結果ページ1枚から
「馬・スコア・着順・オッズ」を同じループ内で束ねて生成するため、
位置依存 ID による取り違えが原理的に起こらない。
④のデータセットはこの不具合を持たない。

## 4. 対応案（未着手・要判断）

本書は報告のみ。以下は選択肢。

| 案 | 内容 | 備考 |
|---|---|---|
| A | `id` を `netKeibaHorseId` ベースの安定 ID に変更 | 本質的な修正。既存キャッシュの移行が必要 |
| B | `scores-cache` のキーを `netKeibaHorseId` に変更 | join だけ安定化。races-cache の id は残る |
| C | join を `netKeibaHorseId` で行うよう読み手側を修正 | 書き込み側は据え置き。影響範囲が最小 |

いずれも本番パイプラインに触るため、④の取得完了を待ってから判断したい。
なお ④のデータセットは本不具合と無関係に正しいので、
**④の分析は本修正を待たずに進められる。**
