# ④ 過去レース一括取得 — リーク対策 設計案

対象: Phase 0 で保留にしていた過去レース一括取得（6ヶ月・約1,730レース規模）。
本書は **実装前の設計案** であり、まだコードは変更していない。

## 0. この取得で白黒つけたいこと

1. 芝×複勝の ROI（現在 -13.0%, CI[-36.2%, +11.7%]）が、標本増加後もプラス圏に触れ続けるか / 0 に収束するか
2. 新馬セグメントでモデル AUC が市場を上回った現象（現在 的中14件）が再現するか
3. 単勝の標本不足（v2 全体で的中17件）を解消できるか

いずれも **バックテスト（過去レースの遡及評価）** であり、リークがあると結論が丸ごと無効になる。

---

## 1. 問題: jockeyScore のリーク

`lib/scraper.ts` の `fetchJockeyStats` は netkeiba の年度別成績テーブルから
**「直近年度の行」** を返す（`parseJockeyYearlyStats` の `years[0]`）。

- **週次のライブ運用では正当**: 予測時点から見て、その行の騎乗はすべて過去。
- **遡及バックフィルでは不正**: 2026-02 のレースを今日スクレイプすると、
  返る 2026 年行には **そのレース後（3〜6月）の騎乗結果が混入** する。

`formScore` 側は `scripts/_probe-newfeatures.ts:127` で既に
`past = past.filter((p) => p.date < cutoff)` の方式で断っている。
jockeyScore にも同じ思想を適用する。

---

## 2. 事前調査で判明した事実（設計を左右する）

実際に netkeiba を叩いて確認した。調査スクリプトは
`scripts/_probe-jockey-yearly.ts` / `scripts/_probe-jockey-staleness.ts`。

### 2-1. 粒度は「年度」までしか取れない

`db.netkeiba.com/jockey/result/{id}/` の年度別テーブルは
`累計 / 2026 / 2025 / 2024 / ...` の行を持つ（列: 0=年度 1=順位 2=1着 3=2着 4=3着 5=着外）。
`/{id}/2025/` のような年度指定 URL は **同じページを返すだけ** で、月次以下の内訳は無い。

→ 「レース前日時点の年度内累計」を安価に取る手段は無い。年度境界で切るのが現実解。

### 2-2. ★年度別成績テーブルは 3週間以上更新が止まっている

丹内（01091）の 2026 年行は **57勝 / 562戦** で、以下すべてで同一値だった:

| 時点 | 2026年行 |
|---|---|
| scores-cache の computedAt=2026-07-10 | 57勝 / 562戦 |
| scores-cache の computedAt=2026-08-01 | 57勝 / 562戦 |
| 本日 2026-08-02 ライブ取得 | 57勝 / 562戦 |

一方、**同じ丹内は 2026-07-11〜07-26 に 51回騎乗している**（races-cache × results-cache で確認）。
騎乗しているのに数字が動いていない。

- CDN キャッシュではない: CloudFront は `Miss`、キャッシュバスター + `no-cache` でも同値。
- 単発事象でもない: **2時点以上のスナップショットを持つ 118騎手すべてで rides の変化が 0**。

→ netkeiba 側の集計ラグ（3週間以上）が確定。

**この発見の含意は 2つ:**

- (a) **リーク量はラグの分だけ小さい** が、2026-02 のレースに対しては依然として数ヶ月分の未来混入。
- (b) **本番のライブ運用でも jockeyScore は数週間古い値を使っている。**
  これはリークとは別種の品質問題（後述 §6）。
  同時に「当年行のほうが情報が新しい」という前提が実は成立しておらず、
  **年度境界で切ることの実質的な損失は小さい** ことも意味する。

### 2-3. 騎手はわずか129名 — 馬と違い全件取得が安い

races-cache のユニーク騎手は 129名。1騎手1リクエストなら約3分。
**馬（数千〜1万規模）とはコスト構造が根本的に違う。**

## 3. 設計方針: 「生データを1回取得し、レース日ごとにオフラインで導出」

②で確認済みの原則（memory: キャッシュ設計は生データも保存）をそのまま適用する。
**jockey も horse も同じ形にそろえる。**

```
[取得フェーズ] エンティティ単位で生データを1回だけ取る（レース単位ではない）
    騎手 129名  → 年度別テーブル全行をそのまま保存
    馬 約1万頭  → 全戦績テーブルをそのまま保存
        ↓
[導出フェーズ] レース日を cutoff にオフラインで per-race に切り出す（再取得不要）
    jockeyScore  ← 年度 < レース年 の行のみ
    formScore    ← p.date < レース日 の行のみ（既存 formScore 対策と同じ）
```

この分離により、**ルールを変えても再スクレイピング不要**（MIN_RIDES の閾値変更、
「前年のみ」vs「過去全年合算」の比較などをオフラインで試せる）。

### 3-1. jockeyScore の cutoff ルール

> レース年 Y のレースには、**年度 < Y の行のみ** を使う。
> 年度 ≥ Y の行と「累計」行（当年を含むため）は絶対に使わない。

| 段階 | 条件 | 使うもの |
|---|---|---|
| 1 | 既定 | 年度 Y−1 |
| 2 | rides < 30 (`MIN_RIDES_FOR_YEAR`) | Y−1 + Y−2 |
| 3 | なお rides < 30 | 年度 < Y の全行を合算 |
| 4 | 年度 < Y の行が皆無（当年デビュー） | **`null`** |

現行の「新しい方へフォールバック」を **必ず過去方向へ倒す** よう反転させる。

段階4の `null` は既存の欠損パスに乗る:
`lib/engine.ts:52` の `calculateStrength` は `jockeyScore == null` のとき
jockey の重み 0.15 を form/pedigree へ再配分する。デフォルト65 で埋めない
（「欠損」と「平均的な騎手」を混同しない）ため、追加実装は不要。

### 3-2. 実装単位

| 項目 | 内容 |
|---|---|
| `fetchJockeyYearlyTable(jockeyId)` | 新設。年度別行を **全行** そのまま返す（集約しない） |
| `lib/jockey-yearly-cache.json` | 新設。jockeyId → 全年度行 + fetchedAt。約129件 |
| `resolveJockeyStats(rows, raceYear)` | 新設。純関数・I/O 無し。§3-1 のルールを適用 |
| `fetchJockeyStats` | **現状維持**（本番ライブ経路が使用中。§6 で別途扱う） |

完了年度の行は不変なので、このキャッシュの再取得は年跨ぎと新規騎手追加のときだけでよい。

## 4. 既存 v2 データとの整合（要判断ポイント）

既存の v2 228レースは **2026年行（当年・進行中）** でスコアされている
（丹内の保存値 57勝/562戦 = 2026年行と完全一致で確認済み）。

バックフィル分だけ Y−1 ルールにすると、**同一データセット内に2つの特徴量定義が混在** し、
③でやっているセグメント比較が交絡する。

| 案 | 内容 | 評価 |
|---|---|---|
| **A** | 既存分も含めて **全レースを Y−1 ルールで再導出** | **推奨** |
| B | 既存は据え置き、バックフィル分のみ新ルール | 母集団が2分割され、①②③すべての問いが弱まる。非推奨 |

**A を推奨。** 対象は全て2026年のレースなので、全騎手が2025年行から算出される。
騎手ページを129回叩き直すだけで、既存分もオフライン再計算できる。

### 4-1. 出力先は分ける（本番を壊さない）

再導出結果は **`lib/scores-cache-v3.json`（新規ファイル）** に書き、
本番が読む `lib/scores-cache.json` は触らない。

- 本番パイプラインへの影響ゼロ
- **v2（当年行・リークあり）と v3（Y−1・リーク無し）の A/B が明示的に取れる**
  → 「リーク除去で結論がどう変わったか」を数値で示せる
- 分析スクリプト（`sim-thresholds*.ts`）はキャッシュパスを引数化するだけで対応

`CURRENT_MODEL_VERSION` は v3 を追加し、再導出分に付与する。

### 4-2. 受け入れる副作用（明示）

Y−1 ルールでは、分析期間（2026年内）で **jockeyScore が騎手ごとに定数** になる。
年内の調子変動は捉えられない。

ただし §2-2 の通り **元データが3週間以上遅れている以上、年内変動は元々ほとんど捉えられていない**。
失うものは小さく、得られる正当性は大きい、というのが判断根拠。

なお当年デビュー騎手は `null` になる。現行の保存値で 2026年 rides < 100 は 37名 / 128名だが、
その大半は 2025年以前の騎乗実績を持つベテラン（騎乗数の少ない層）で、
真に 2025年行を持たない騎手はごく少数と見込まれる。**実装時に実測して報告する。**

## 5. 取得規模の見積もり

races-cache の実測から外挿した。

- 実測: 372R / 延べ出走 4,829 / ユニーク馬 3,972（11開催日）
- 累積ユニーク曲線を占有モデル `U(E) = N(1 − e^(−E/N))` で当てはめると **N ≈ 12,000**
  （E=4,829 で U=3,976、実測3,972 とほぼ一致）

6ヶ月（約52開催日）へ外挿:

| 項目 | 概算 |
|---|---|
| レース数 | 約 1,759R |
| 延べ出走 | 約 22,834 |
| **ユニーク馬** | **約 10,200** |
| ユニーク騎手 | 129 |
| リクエスト総数 | レース 1,759〜3,518 + 馬 10,200 + 騎手 129 ≒ **12,100〜13,900** |
| **所要（1.2s/req）** | **約 4.0〜4.6 時間** |

ご提示の 4.5〜5時間見積もりと整合。
なお過去レースは結果ページ1枚に馬ID・騎手ID・オッズ・着順が揃う可能性があり、
出馬表と結果の2枚を1枚に減らせれば下限側（約4.0時間）になる。実装時に確認する。

### 5-1. 中断耐性を必須要件にする

4時間超の処理は **必ず中断される**（前回セッションも PC 再起動で落ちている）。

- エンティティ単位（馬ID / 騎手ID）で **逐次チェックポイント保存**、再実行時は未取得分のみ
- 取得失敗は既存エントリを上書きしない（`fetch-payouts.ts` で確立済みの方針を踏襲）
- 進捗ログを一定件数ごとにファイルへ書き出し、別セッションからでも進行状況を確認可能

## 6. 本設計の範囲外（別issue）

**本番のライブ経路も数週間古い jockeyScore を使っている**（§2-2-b）。
これはリークではなく鮮度の問題であり、④の目的（バックテストの正当性確保）とは別軸。

train/serve skew の観点では、④で「Y−1 ルール下で芝×複勝が有効」と結論が出た場合、
**本番も同じ定義に揃えないと結果が転移しない** という論点がある。
ただし本番変更は④の検証結果を見てから判断すべきなので、
**④には含めず、フォローアップとして切り出す。**

---

## 7. 実装順序（案）

1. `fetchJockeyYearlyTable` + `jockey-yearly-cache.json` + `resolveJockeyStats` を実装（129リクエスト・約3分）
2. **既存 v2 228レースを v3 として再導出**し、`scores-cache-v3.json` を作成
3. **v2 vs v3 で ②③ を再実行** — リーク除去で結論がどう動くかを先に確認（ここで大きく壊れるなら④の設計を見直す）
4. 問題なければ 6ヶ月バックフィル本体に着手（中断耐性つき・約4〜4.6時間）
5. 拡大後データで §0 の3つの問いを再検証

**手順3を挟むのが要点。** 4時間の取得に入る前に、リーク除去の影響を既存データで先に見ておく。
